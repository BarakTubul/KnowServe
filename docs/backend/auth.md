# Backend auth, sessions and identities

**Status:** Target spec (M1), revised 2026-11-06 for **Firebase Authentication** (OPEN-24) and the session, Demo, quota and department decisions of OPEN-25. Not implemented: the legacy code uses JWT, self-registered roles and no email verification (see "Current implementation").

## Purpose
This is the focused FastAPI auth module. Credentials are handled by **Firebase Authentication** (Email/Password, Google Sign-In, and Anonymous Authentication for Try Demo). The API verifies a Firebase ID token once and then issues its **own opaque, DB-backed session**. CSRF, the Demo identity and its conversion, the single private Admin, the persisted active department and the usage quotas stay in KnowServe. The API never receives or stores a password. Access-control rules are in `../cross-cutting/security-and-permissions.md`. Approved decisions: OPEN-04, OPEN-12, OPEN-14, OPEN-24, OPEN-25 (`../open-decisions.md`). OPEN-15 and the registration part of OPEN-14 are amended by OPEN-24 (AUTH-02, AUTH-03).

## Target requirements
| ID | Requirement | Milestone |
|---|---|---|
| AUTH-01 | Users sign up with **email and password through Firebase Authentication** (client SDK), either from the login screen or from a Demo session (AUTH-34). The email address is the login identifier; there are no usernames in M1. KnowServe stores **no password and no password hash** (no custom password storage). A `users` row is created on the first successful session exchange (AUTH-30), keyed by the Firebase `uid`, with the email normalized (trimmed, lower-case). | M1 |
| AUTH-02 | Sign-in failures and password-reset requests do not reveal whether an email is registered: Firebase **email enumeration protection stays enabled**. **Known deviation from OPEN-14 (OPEN-24):** the Firebase client signup returns "email already in use", so signup reveals an existing email. A server-side signup that hides it would need custom mail and password handling, which is out of scope. | M1 |
| AUTH-03 | Password policy (amends OPEN-15): the minimum is **8 characters** with **no composition rules**, long passphrases and Unicode accepted, **enforced by Firebase's password policy in `Require` mode**. Availability on the standard Firebase Authentication project (no Identity Platform upgrade in M1) is verified in the actual Firebase console before enforcement is relied on; if the project cannot enforce it without upgrading, the limitation is reported and the Owner approves any change to this requirement or any Identity Platform upgrade (OPEN-26, N3). Because KnowServe never sees a password, the common-password blocklist and breach check of OPEN-15 are **not enforceable server-side and are dropped**; the frontend may warn, but that is UX only. The 8-character minimum is a demo choice and is not described as meeting the stricter NIST single-factor recommendation. | M1 |
| AUTH-04 | There is exactly one private **Admin** identity: a Firebase account created manually in the Firebase console and bound to its Firebase `uid` by a **one-time, idempotent provisioning command** that sets the Admin kind in the `users` table (configuration: `uid` and email, no secret). Admin authorization is stored and enforced in KnowServe's database and is checked on every Admin request; it is never derived from the email, a client-supplied value or a token claim. The Admin may sign in with **either Email/Password or Google Sign-In**; both methods are linked to the same Firebase account through the safe linking of AUTH-32, so there is one `uid`. Admin authorization is determined **exclusively** by that provisioned `uid` and its KnowServe database identity, never by email address, sign-in provider, a client-supplied role or frontend state (OPEN-26, O1). No public API or UI path can create or elevate to Admin, and there is no role-management feature in M1. | M1 |
| AUTH-06 | A successful session exchange (AUTH-30), Demo start (AUTH-16) or conversion (AUTH-34) creates a new **opaque random session token**. Only a **hash** of the token is stored in PostgreSQL. The token is set in a `Secure`, `HttpOnly`, `SameSite=Lax`, **host-only** cookie on the API host (OPEN-04). Any pre-existing session id is not reused, which rotates the session against fixation. The Firebase ID token is verified, then discarded; it is never stored or logged. KnowServe sessions are not Firebase Session Cookies. | M1 |
| AUTH-07 | An invalid, expired, forged, wrong-audience or disallowed-provider ID token returns the same `401` with the same generic message (unverified email: AUTH-13). The one deliberate exception is a token that passes every signature, issuer, audience and expiry check but whose sign-in is older than the freshness window returns `401 REAUTH_REQUIRED` (all other failures stay the generic 401), so the client can ask for the credential again (AUTH-30). A wrong email or password is reported by Firebase with its generic invalid-credential error. | M1 |
| AUTH-08 | Logout revokes the server-side session (the row is invalidated) and clears the cookie; the frontend also signs out of Firebase. For a Demo identity, logout ends the session only; the Demo data is removed by AUTH-35. | M1 |
| AUTH-09 | A "current identity" endpoint returns the identity kind (registered, demo, admin), its display data, the sign-in method, the active department (or none), the session expiry time and the CSRF token (AUTH-14) for a valid session, and `401` otherwise. | M1 |
| AUTH-10 | Each request is validated by hashing the cookie token and looking up an unexpired, unrevoked session. **Registered, Admin and Demo sessions expire 24 hours after creation.** The lifetime is absolute: there is no idle timeout, no sliding renewal and no refresh endpoint, so continued use never extends a session. Expiry is enforced by the backend from the stored `expires_at`; an expired or revoked session gets `401`. After expiry the user signs in again (a fresh Firebase sign-in, AUTH-30). The lifetime is configuration. | M1 |
| AUTH-11 | Admin-only routes return `403` to registered users and Demo users (SEC-03). | M1 |
| AUTH-13 | **Email verification is mandatory for password signups.** Firebase sends the verification email. The session exchange rejects any token with `email_verified = false` with `403 EMAIL_NOT_VERIFIED` and creates no session. An unverified account cannot access protected resources. Google accounts arrive with a verified email, and the claim is still checked. Verifying the email never creates a session by itself: the user then signs in, or, if the verification happened more than the freshness window after their last sign-in, completes the explicit reauthentication of AUTH-30. | M1 |
| AUTH-14 | Every cookie-authenticated state-changing request requires **both** a valid CSRF token bound to the session **and** an `Origin` matching an allowed frontend origin; otherwise it is rejected (OPEN-04). CORS is not treated as a CSRF defense. The token is returned by AUTH-09 and by the endpoints that create a session, and is sent as `X-CSRF-Token`. The session-creating endpoints (`POST /v1/auth/session`, `POST /v1/demo/start`) have no session yet, so they require the Origin check and a valid fresh ID token instead of a CSRF token. | M1 |
| AUTH-15 | Brute-force protection is Firebase's for sign-in, signup and reset (not tunable by us, not duplicated). KnowServe adds only: **Demo creation 5 per hour per IP** (configurable) and the usage quotas of AUTH-36. | M1 |
| AUTH-16 | **Try Demo** uses **Firebase Anonymous Authentication**. The client signs in anonymously and calls `POST /v1/demo/start` with the ID token; the backend verifies it (provider `anonymous`), creates an internal **Demo identity** (a `users` row of kind `demo` keyed by the Firebase `uid`, no email) and a KnowServe DB session (AUTH-06). No registration is required. The Demo session expires **24 hours after creation** (AUTH-10) and a Demo identity cannot start a new session after its own 24 hours (`DEMO_EXPIRED`, the client starts a new Demo), so reuse never extends it. Demo users may switch departments (AUTH-17), keep history isolated per Demo identity and department (SEC-16), cannot call Admin routes (AUTH-11) and can reach only authorized Demo data. Firebase identifies the user; KnowServe remains responsible for authorization and isolation. | M1 |
| AUTH-17 | Every registered user, Demo user and the Admin may select and switch among **all** seeded departments (OPEN-12, Demo Mode); selecting a department is never a permission elevation, and document access is checked on every relevant backend operation under the existing department-access model. The user's **last active department is persisted in PostgreSQL** (`users.last_active_department_id`) and restored on the next session; the session carries the active department. On first login there is none, so an operation that needs one returns **409 `ACTIVE_DEPARTMENT_REQUIRED`** (OPEN-14) and the frontend requires a selection. A switch never carries over data or context from the previous department (SEC-10). | M1 |
| AUTH-18 | JWT is **not** used as the primary session scheme (the Firebase ID token is used only to create a session), and Starlette's signed-cookie `SessionMiddleware` is **not** used as the session store. | M1 |
| AUTH-19 | **Same-origin API route** (mechanism of OPEN-04 superseded by OPEN-21, approved provisionally pending spike validation): the browser calls one origin; a Cloudflare Pages Function forwards `/api/v1/*` to the Cloud Run API (`../contracts/proxy.md`). Cookies stay host-only on that origin, so production needs no cross-site cookie and no CORS. The API accepts requests only with the proxy secret (403 `DIRECT_ACCESS_DENIED` otherwise) and trusts the forwarded client IP only after that check. `KS_API_ALLOWED_ORIGINS` is the single app origin used by the Origin check. Cloud Run Domain Mapping and `SameSite=None` workarounds are not used. | M0 spike / M1 |
| AUTH-20 | A departments endpoint returns the five seeded departments (Human Resources, Finance, Engineering, Legal, Sales) with stable ids and slugs. There is no department or user CRUD in the MVP (PROD-03). | M1 |
| AUTH-21 | Auth and security events (session exchange and Demo start success/failure by provider and reason, `EMAIL_NOT_VERIFIED`, account conflict, conversion outcome, logout, session revocation, quota exceeded, Demo cleanup run, admin actions) are audit-logged without ID tokens, session tokens, cookies or CSRF values (MON-04, MON-05). Password signup, verification and reset happen inside Firebase and are not visible to the API. | M1 |
| AUTH-29 | **Firebase Authentication is the only credential system.** Providers enabled: Email/Password, Google and Anonymous (the last only for Try Demo). No other provider, no phone, no email-link or one-time-code login. Email OTP is removed from the MVP (OPEN-24). | M1 |
| AUTH-30 | **Token verification and session exchange.** `POST /v1/auth/session` takes a Firebase ID token and `POST /v1/demo/start` takes an anonymous one. Verification checks the signature, issuer, audience (the Firebase project id) and expiry, plus **freshness** (`auth_time` within a short window, initially 5 minutes, so a stolen old token or a long-lived browser login cannot silently start a new session and thereby extend a session). A stale but otherwise valid token gets `401 REAUTH_REQUIRED` (AUTH-07). **Reauthentication flow:** the client asks the user for their credential again (password via Firebase `reauthenticateWithCredential`, or the Google popup), which refreshes `auth_time`, and retries once. This also covers the verification case: a user who creates a password account and verifies the email later than 5 minutes after signing in, possibly in another tab or browser, signs in or reauthenticates explicitly and then gets a session. No silent path exists, and the session created afterwards still lasts 24 hours from its own creation (AUTH-10). `/v1/auth/session` additionally requires `email_verified = true` and a provider of `password` or `google.com`; `/v1/demo/start` accepts only `anonymous`. It loads or creates the `users` row by `uid` and issues the session. If the `uid` already has a `demo` row and the token is now verified and non-anonymous, the exchange completes the conversion (AUTH-34). The verifier is the Firebase Admin SDK behind an interface; the emulator is accepted only when `KS_ENV` is not `production` and is rejected at startup in production. | M1 |
| AUTH-31 | **Google Sign-In** is offered on the same login screen as email/password (FE-AUTH-02). It uses the Firebase SDK; the API sees only a Firebase ID token and never a Google token. The Admin may use Google as well; Admin rights depend only on the provisioned `uid` (AUTH-04). | M1 |
| AUTH-32 | **Account linking is safe.** There is one KnowServe user per Firebase `uid`, and KnowServe never merges or links accounts by matching email itself. Firebase's "one account per email" setting is enabled. A Google sign-in for an email that already has a password account is completed only after the user signs in with the existing method and links the credential in the client. An **unverified** password account is never linked or trusted. `users.email` is unique (when not null): a different `uid` presenting an already-used email is refused with the generic failure and an audit entry. | M1 |
| AUTH-33 | **Password reset** uses Firebase's reset email. The reset request shows the same confirmation whether or not the email exists (AUTH-02). The reset and verification links open a KnowServe action page that handles success, expired and invalid codes. **Revocation (OPEN-26, O2):** a "sign out everywhere" call (`POST /v1/auth/sessions/revoke-all`, CSRF-protected) revokes all of the user's KnowServe sessions immediately, and so does disabling a user through KnowServe (an internal, non-HTTP operation that sets `users.disabled_at`, revokes the sessions and blocks new ones; no user-administration feature is added). KnowServe does **not** check Firebase account state on each request, so a password reset or an account disabled **externally in Firebase** does not revoke existing KnowServe sessions in M1; they end at their absolute 24 hours, at logout or at revoke-all. This limitation is documented, see Known gaps. | M1 |
| AUTH-34 | **Demo → new Registered account, history preserved.** A Demo user registers by linking an Email/Password or Google credential to the **existing Firebase anonymous account** (Firebase account linking), so the Firebase `uid` stays the same. The backend converts the internal identity from `demo` to `registered` (same `users.id`, so chat history and department-specific history stay attached) only when it receives a valid fresh ID token for that `uid` with a non-anonymous provider and `email_verified = true`, through either `POST /v1/auth/convert` (authenticated by the current Demo session, CSRF and Origin) or the normal exchange (AUTH-30). Until the verification policy is met (password signups need the verification email), the identity stays `demo`. Conversion is one transaction, idempotent (repeating it changes nothing) and safe under partial failure: if Firebase linking succeeded but the KnowServe call did not, the next exchange completes it; if it fails mid-way nothing changes. It revokes the Demo session and issues a new opaque Registered session valid **24 hours from the conversion**, a new authentication event and not an extension of the Demo session (AUTH-06, AUTH-10, OPEN-26 O3); the Firebase `uid`, `users.id`, department contexts and dependent records are preserved. Conversion grants **no** additional document or Admin permissions. A Demo user can convert only into a **new** account: if the email or Google credential already belongs to another Firebase account, Firebase refuses the link, nothing is merged, the Demo history is **not** transferred to the existing account (M1), and the UI offers a normal sign-in instead. A Demo conversion can never produce the Admin. **Evidence scope:** M1 has no chat, so M1 proves identity continuity (same `users.id` and uid) and the preservation of representative dependent records (test-fixture rows that reference `users.id` per department, shaped like the future conversations and messages). The requirement itself, that chat history is preserved, is unchanged, and its end-to-end evidence is an M4 criterion (CHAT-18). | M1 (identity and records) / M4 (chat history) |
| AUTH-35 | **Demo retention and cleanup.** An unconverted Demo identity's history is kept **48 hours from Demo creation**; once per day an automatic cleanup deletes the Demo identities older than that, with their sessions, chats and other rows. Cleanup is idempotent, bounded per run, deletes only rows still of kind `demo` (re-checked inside the delete transaction, so a conversion that races with it wins and converted data is never deleted), and logs counts only. The daily trigger is one QStash schedule calling a dedicated Worker maintenance endpoint that requires a valid QStash signature and takes no caller-controlled parameters (the narrow SEC-14 exception). Firebase anonymous accounts are separate from these rows: M1 uses standard Firebase Authentication without Identity Platform and implements no custom cleanup of them, and the database cleanup never depends on them (OPEN-26, N2). | M1 |
| AUTH-36 | **Usage quotas and AI budget guard.** Per-day question limits, counted per UTC day on the user id: **Demo 20, Registered 100, Admin 100**; exceeding a limit returns `429 QUOTA_EXCEEDED` with the retry time. Rate limits: Demo creation 5 per hour per IP (`429 RATE_LIMITED`). All values are configuration. A **global AI usage guard** keeps a daily total and a kill switch; when the global threshold is reached or the switch is on, AI requests are refused with `503 AI_UNAVAILABLE` while sign-in, the library, the viewer and history keep working (COST-05, INFRA-10). The initial **global quota is 100 AI questions per UTC day** across KnowServe, configurable. It is an operational usage guard, not a guaranteed monetary spending cap (OPEN-26, N1). M1 delivers the counters, guard, configuration and 429/503 behavior; they are applied to chat in M4 (CHAT-19). Because the counter is per user id, a converted Demo user keeps one counter and moves to the Registered limit. | M1 (mechanism) / M4 (applied to chat) |

## Current implementation (LEGACY, not migrated)
- `routers/auth.py`, `services/auth_service.py` and `utils/jwt.py` issue a **JWT** (python-jose) with `user_id`, `role` and `department_id`. It is read from the `token` cookie or `Authorization: Bearer`, and the cookie has `secure=False`.
- Passwords are hashed with passlib argon2 (`utils/hashing.py`). The target stores no passwords at all (AUTH-01).
- `RegisterRequest.role` is client-controlled (`employee`/`manager`/`admin`), so anyone can register as Admin if none exists. This contradicts AUTH-04.
- Roles employee/manager/admin; a user has a single fixed `department_id`.
- There is no email verification, CSRF, rate limiting, Try Demo, department switch, departments endpoint, quotas or audit logging. `/auth/me` returns the raw JWT payload.
- The legacy signup schema requires an uppercase letter and a digit; AUTH-03 drops those composition rules.

## Known gaps
Every AUTH requirement is unimplemented on the target stack. Consequences of the Firebase decision that are not hidden:
- **Cannot be preserved without custom implementation:** the password blocklist and breach check (OPEN-15), hiding an existing email at signup (OPEN-14), a tunable per-account lockout, and ending KnowServe sessions when a password is reset or a Firebase user is disabled. They are dropped or accepted as stated above, and a custom replacement was rejected because it would mean custom password handling.
- A password reset or a disabled Firebase user does not end existing KnowServe sessions until the 24 hours end or the user signs out everywhere (AUTH-33). Accepted limitation (OPEN-26, O2).
- The 8-character `Require` password policy must be verified in the real Firebase console (AUTH-03). If it cannot be enforced without an Identity Platform upgrade, that is reported to the Owner; M1 does not upgrade.
- Firebase behavior for account linking, anonymous-to-permanent linking, token claims after linking, enumeration protection, the password policy and unverified accounts is from general knowledge and must be checked against current documentation and the real project (M1-01, M1-08).
- Firebase anonymous accounts are not deleted by the database cleanup (AUTH-35; OPEN-26).
- Quotas and the AI guard are exercised in M1 through tests only; chat applies them in M4. Likewise, Demo → Registered history preservation is proven in M1 on representative records and on real chat history in M4.
